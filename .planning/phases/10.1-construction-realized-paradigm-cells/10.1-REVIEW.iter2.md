## Warnings

### WR-01: `_saveConstructionRule` risks `setState` after dispose in the `finally` block on the success path

**File:** `lib/features/morphology/presentation/rules/rule_editor/rule_editor_body.dart:340-350`

**Issue:** After a successful save, `Navigator.of(context).pop()` is called at line 340. On the frame when the widget is disposed, the `finally` block at line 349 calls `setState(() => _saving = false)`. Although the guard reads `if (mounted)`, there is a race: `Navigator.pop()` schedules disposal asynchronously; the `finally` block may execute on the same microtask before the widget is formally unmounted, but it may also execute after. The guard is present and protects against the crash, which is correct. However, the validation early-return paths (lines 275-299) each contain `_saving = false` inside their own `setState` calls AND the `finally` block will also set `_saving = false` again immediately after return — this is a redundant double `setState` on every validation failure path, causing an unnecessary extra rebuild.

**Fix:** Remove the `_saving = false` from the validation early-return `setState` blocks and rely solely on the `finally` guard for all `_saving` resets:

```dart
if (name.isEmpty) {
  setState(() => _validationError = 'Rule name is required.');
  return;  // finally handles _saving = false
}
if (_selectedConstructionId == null) {
  setState(() => _validationError = 'Select a construction.');
  return;
}
if (_selectedWordSlotId == null) {
  setState(() => _validationError = 'Select a word slot.');
  return;
}
```

### WR-02: `ParadigmConstructionFilled._tokenPhonemic` uses `ipa` for `ParticleToken` — feeds post-rewrite allophones to `romanize()`

**File:** `lib/features/grammar/domain/paradigm_cell.dart:144-147`

**Issue:** `_tokenPhonemic` extracts each token's "phonemic" contribution for the aggregate `ParadigmConstructionFilled.phonemic` field, which is documented as the pre-rewrite form that callers must pass to `romanize()`. For `WordSlotToken` the correct `phonemic` field is used. For `ParticleToken`, `ipa` is used — which is the post-rewrite surface form stored on the lexeme row. If a particle's IPA is an allophone (e.g. `[z]` from underlying `/s/` after a rewrite), `romanize()` will receive the wrong input and produce an incorrect romanization for the particle's portion of the construction cell.

The `ParticleToken` type already carries an optional `romanization` field (populated from the lexeme's stored romanization column). This is the correct pre-computed romanized form and should be the value passed via `phonemic` so that `romanize()` either receives a romanization-ready string or the IPA as fallback.

**Fix:**

```dart
static String _tokenPhonemic(ConstructionToken t) => switch (t) {
  ParticleToken(:final romanization, :final ipa) => romanization ?? ipa,
  WordSlotToken(:final phonemic) => phonemic,
};
```

### WR-03: Delete icon in `_ConstructionRuleCard` deletes immediately without confirmation — single tap causes irreversible data loss

**File:** `lib/features/grammar/presentation/inflectional_rules/inflectional_rules_page.dart:207-213`

**Issue:** The delete `IconButton` calls `dao?.deleteRule(rule.id)` directly on tap. The code comment explicitly notes "deletes immediately (no confirm)". Deletion is immediately reflected in the reactive paradigm — all construction-realized cells revert to inflectional-only results on the next render. The CASCADE on `ConstructionRulePOS` removes all junction rows. There is no undo path and no soft-delete toggle. A single misclick permanently removes the rule.

Morphological rules in the same file's sibling `RulesPage` typically guard destructive actions. The asymmetry between the two delete UX patterns is a usability correctness issue, not just a style preference, because the user cannot recover from an accidental tap.

**Fix:** Wrap the delete call in a brief confirmation dialog:

```dart
onPressed: () async {
  final confirmed = await showDialog<bool>(
    context: context,
    builder: (_) => AlertDialog(
      title: const Text('Delete construction rule?'),
      content: Text('Delete "${rule.name}"? This cannot be undone.'),
      actions: [
        TextButton(
          onPressed: () => Navigator.pop(context, false),
          child: const Text('Cancel'),
        ),
        FilledButton(
          onPressed: () => Navigator.pop(context, true),
          child: const Text('Delete'),
        ),
      ],
    ),
  );
  if (confirmed == true) {
    final dao = ref.read(constructionRuleDaoProvider);
    await dao?.deleteRule(rule.id);
  }
},
```

### WR-04: `_buildConstructionForm` conditionally calls `ref.watch` — Riverpod hook ordering violation

**File:** `lib/features/morphology/presentation/rules/rule_editor/rule_editor_body.dart:641-645`

**Issue:** The construction form layout calls `ref.watch(constructionSlotsProvider(_selectedConstructionId!))` only when `_selectedConstructionId != null`:

```dart
final slotsAsync = _selectedConstructionId != null
    ? ref.watch(constructionSlotsProvider(_selectedConstructionId!))
    : null;
```

`_buildConstructionForm` is called unconditionally from `build`, so this conditional `ref.watch` violates Riverpod's requirement that the set of watched providers be stable across rebuilds. If `_selectedConstructionId` transitions between null and non-null across frames, Riverpod may miss invalidations or emit stale slot data. The conditional also means the provider subscription is only created after the user selects a construction — a rebuild that occurs while the widget is transitioning from no-construction-selected to construction-selected could render with stale slot data.

**Fix:** Watch unconditionally, using a sentinel id that returns an empty list:

```dart
// Always watch so the subscription is stable across rebuilds (Riverpod hook ordering).
final slotsAsync =
    ref.watch(constructionSlotsProvider(_selectedConstructionId ?? 0));
final slots = _selectedConstructionId != null
    ? (slotsAsync.asData?.value ?? const [])
    : const <ConstructionSlot>[];
```

Verify that `constructionSlotsProvider(0)` returns an empty stream gracefully (there is no construction with id=0 in the DB, so the query returns empty list — confirmed safe).

### IN-03: `_identicalBindingGroup` returns the first rule rather than the full group when all rules have unique bindings

**File:** `lib/features/grammar/domain/paradigm_engine.dart:257-269`

**Issue:** When no two rules in `topGroup` share an identical binding map, `_identicalBindingGroup` returns "a single-element list (the first element)". The docstring says callers use `length > 1` to detect ambiguity, which is correct — but the reduction `byKey.values.reduce((a, b) => a.length >= b.length ? a : b)` silently discards all but one rule from the top group when all rules have unique bindings. The caller then runs `intra-specificity fall-through` only over that single rule, skipping the remaining top-group candidates. This is a logic bug: the function is supposed to identify only the identical-binding subset for ambiguity detection, not filter the top group for fall-through.

Looking at the call site (line 146-149): if `identicalGroup.length > 1`, ambiguity is returned early; otherwise the code falls through to the `for (final candidate in topGroup)` loop at line 156. The `identicalGroup` is only used for the ambiguity check, not for the fall-through loop. The fall-through loop correctly iterates `topGroup` (all top-group candidates). So the discarded rules from `_identicalBindingGroup` do not affect execution. The function's single-rule return value is only used to assert `length > 1`, which is false for unique-binding cases — the outcome is correct. The naming and docstring are misleading, not the logic.

**Fix:** Clarify the docstring to prevent future misunderstanding:

```dart
/// Returns the largest group of rules in [topGroup] that share an identical
/// binding map. If no two rules share identical bindings, returns the first
/// element as a length-1 list (only the return value's length matters to
/// callers — they use `length > 1` to detect ambiguity; the actual list
/// contents are not used in the non-ambiguous path).
```

### IN-04: `build-release-macos.sh` uses BSD `sed -i ''` — fails on GNU/Linux CI runners

**File:** `scripts/build-release-macos.sh:26`

**Issue:** `sed -i '' "s/..."` is BSD sed syntax. GNU sed (Linux) rejects the empty-string argument. Since `set -euo pipefail` is set, the script would fail loudly rather than silently if run on a Linux runner — but the error message (`sed: 1: "pubspec.yaml": invalid command code p` or similar) is confusing without knowing the root cause.

The script is intentionally macOS-only (filename and usage comment both say "macOS"), so this is not a functional bug in the current workflow. The `Makefile` only invokes it via `bash scripts/build-release-macos.sh`, and CI presumably only runs this on macOS runners.

**Fix:** Add an OS guard comment and, optionally, a runtime check:

```bash
# macOS-only: BSD sed syntax. GNU sed (Linux) requires 'sed -i' without ''.
# This script is not intended to run on Linux.
if [[ "$(uname)" != "Darwin" ]]; then
  echo "Error: build-release-macos.sh must be run on macOS." >&2
  exit 1
fi
sed -i '' "s/^version: .*/version: ${VERSION}+1/" pubspec.yaml
```
