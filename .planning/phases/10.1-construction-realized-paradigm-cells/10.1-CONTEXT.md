# Phase 10.1: Construction-Realized Paradigm Cells - Context

**Gathered:** 2026-04-13
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase bridges Phase 4's paradigm viewer with Phase 10's constructions. Users can define construction rules — a new rule kind alongside inflectional rules — that realize paradigm cells analytically. A "future tense" cell for Verb can be defined as `FUT-AUX + [imperfective form of this verb]`. Constructions and morphological rules **compose**: the inflectional rule fires first (transforming the root), and the construction wraps the resulting form in particles. Neither replaces the other.

Out of scope: changing the Constructions page itself; phrase-level parsing in the scratchpad; any cross-word agreement logic.

</domain>

<decisions>
## Implementation Decisions

### Rule Model

- **D-01:** Construction-realization is a **new rule kind** in the inflectional rule system — not a per-word annotation and not an extension of `ParadigmCellOverrides`. It follows the same feature-binding model as inflectional rules: the user selects dimension levels (or leaves bindings open), exactly as in the existing inflection rule editor flow.
- **D-02:** The rule editor gains a new "construction rule" variant. Instead of a DSL pattern string, the user picks: (a) a construction from the lexicon, (b) which slot in that construction is the "word slot" (user-designated), and (c) which form the word slot resolves to — either base/uninflected form or a reference to another paradigm cell.
- **D-03:** **Per-POS default + per-word override.** Construction rules are POS-scoped (like inflectional rules) and apply to all words of that POS. Individual words can override or suppress the construction assignment for specific cells (via the existing `ParadigmCellOverrides` mechanism or a parallel per-lexeme table — planner to decide exact shape).

### Composition Model

- **D-04:** Construction rules and inflectional rules **compose additively**. For a cell with both: the inflectional chain fires first on the root, producing an `inflected_form`. The construction's word slot then resolves to `inflected_form` (not the bare root). The final cell output is the assembled construction string: e.g. `"kos cazas"` = particle + inflected form.
- **D-05:** If the word slot references another paradigm cell (not base), that cell's own fully-resolved output (including its own inflectional + construction composition) is used — subject to cycle detection (D-09).
- **D-06:** Word slot form resolution: **two options the user sets per rule** — (a) base/uninflected root form, or (b) reference to another specific paradigm cell. When base is selected and an inflectional rule also binds the same cell, the inflected form is used (D-04 composition).

### Resolution Chain

- **D-07:** Construction rules sit **highest in the resolution chain** for display purposes. Full chain: construction rule → per-word manual override → inflectional rule → marker → uncovered. However, construction rules and inflectional rules compose (D-04) rather than one winning over the other — the resolution chain determines display precedence, not mutual exclusion.
- **D-08:** When a cell has both a construction assignment and a morphological rule, **no warning is shown**. The construction silently wraps the morphological output. This is expected and correct behavior.

### Circular Dependency Detection

- **D-09:** When the word slot references another paradigm cell, a **cycle detector** must run before resolving. A new sealed variant `ParadigmUnresolvable` is added to the `ParadigmCell` hierarchy (alongside `Filled`, `Uncovered`, `Ambiguous`, `Unmarked`). It renders with a warning icon and a tooltip showing the full cycle path (e.g. `"Cell FUT → Cell COND → Cell FUT"`). No runtime exception — cycles are a named, handled state.

### Cell Rendering

- **D-10:** Construction-realized cells use the **same two-line layout** as morphological cells (romanization + IPA). A small badge/icon distinguishes the cell as analytically realized (construction-via). Phonotactic violation highlighting applies to the rendered output as usual.
- **D-11:** A new `ParadigmConstructionFilled` sealed variant (or similar name — planner to decide) holds the assembled construction output: `List<ConstructionToken>` (each token is either a particle IPA or the word-slot form) so the renderer can compose the display string and apply violation highlighting to the whole output.

### Storage

- **D-12:** Claude's discretion on exact storage shape. Constraints: (a) construction rules must be POS-scoped and feature-bound, mirroring `MorphologicalRules`; (b) the word-slot designation and form reference must be stored per rule; (c) per-word override of a POS-level construction rule must be expressible. A new table (e.g. `ConstructionRules`) or a new `kind` on `MorphologicalRules` are both valid — planner to evaluate and decide. Schema version bump required (current: v15).

### UI Entry Point

- **D-13:** Construction rule creation follows the same flow as inflectional rules: either click a paradigm cell (pre-selects that cell's feature bindings) or click the "New rule" button in the rule editor. The rule editor dialog gets a new "type" selector that includes "construction" alongside the existing inflectional/derivational kinds.

### Claude's Discretion

- Exact table name and column shape for construction rules
- Whether `ConstructionRules` is a separate table or a `kind='construction'` row on `MorphologicalRules`
- Per-word override storage shape (extend `ParadigmCellOverrides` vs. new join table)
- Badge/icon design for construction-realized cells
- Exact `ParadigmConstructionFilled` variant name and token struct shape

</decisions>

## Existing Code Insights

### Reusable Assets
- **`computeParadigmCell` in `paradigm_engine.dart`**: Pure function with sealed return type — cleanly extensible. Construction rule resolution should be a new pre-pass or integrated step, not a wrapper.
- **`ParadigmCellOverrideDao`**: Keyed by `(lexemeId, featureSetJson)` — the per-word override pattern can be mirrored for per-word construction suppression.
- **`ConstructionPreview` widget**: Already resolves gloss_tag slots to particles and pos slots to sample words — the same lookup logic serves word-slot resolution in the paradigm engine (headless version).
- **`RuleEditorDialog`**: The existing inflectional rule editor dialog is the UI target for the "construction rule" variant; it already handles feature-binding selection and could be extended with a rule-type switcher.

### Established Patterns
- **Feature-binding model** (`FeatureBindingsConverter`, `featureSetKey`): Construction rules reuse this verbatim — same `{dimId: levelId}` binding map.
- **Sealed `ParadigmCell` hierarchy**: Callers already switch exhaustively on subtypes — adding new variants forces all callers to handle them (compile-time safety).
- **Drift schema migrations**: `if (from < N)` guards in `onUpgrade` with safety-net `beforeOpen` ALTER TABLE — follow Phase 10 v15 pattern.
- **`StreamProvider.family`** pattern for reactive per-ID data — construction rule list per POS follows the same pattern as `watchSlotsFor(constructionId)`.

### Integration Points
- **`paradigm_engine.dart` `computeParadigmCell`**: Construction rule resolution must integrate here — either as a pre-pass (if construction always wraps) or a parallel result assembly step.
- **`paradigm_table_widget.dart`**: New `ParadigmConstructionFilled` and `ParadigmUnresolvable` variants require new rendering branches in the cell builder switch.
- **`RuleEditorDialog`**: New "rule type" selector; construction type shows construction picker + word-slot designator instead of DSL text field.
- **`app_database.dart`**: New table(s) + v16 migration + `@DriftDatabase` tables list update.

</code_context>

<specifics>
## Specific Ideas

- Composition model: "kos cazas" — particle from lexicon (unchanged) + morphologically-inflected word form. The particle never changes; the word form comes from the existing paradigm engine output for that cell.
- Conditional example: "cond = imperfective + 'to go' particle" — word slot references the imperfective paradigm cell; the 'to go' particle comes from a gloss_tag slot.
- Subjunctive example: "subj = -a suffix (inflectional rule) + 'kos' particle (construction)" — both compose on the same cell.
- Cycle path display: `"Cell FUT → Cell COND → Cell FUT"` in tooltip on `ParadigmUnresolvable` cells.

</specifics>
