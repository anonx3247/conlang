# Phase 10.1: Code Review Report

**Reviewed:** 2026-04-14T17:14:18Z
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

Phase 10.1 introduces construction-realized paradigm cells: a new `ConstructionRules` table (v16 schema), `ConstructionRuleDao`, domain model (`ConstructionRule`, `FormReference` hierarchy), a post-pass in `generateParadigm` / `resolveConstructionCell`, and full UI wiring through `InflectionalRulesPage`, `_ConstructionFilledCell`, and `RuleEditorBody`.

The core engine logic is solid and well-tested. The cycle-detection and cache threading in `resolveConstructionCell` are correct. The `FormReference.fromJson` defensive parsing, the D-01 specificity delegation, and the D-112 phonemic/form split are all properly implemented.

Four warnings were found — none are crashes but each represents a real correctness or silent-failure risk:

1. **Construction rule lookup by name is not unique** — `_ParadigmCellWidget`'s click handler matches a construction rule by `constructionName` (rule name string), which is not unique-constrained in the DB. Two rules with the same name would resolve to the first one, silently editing the wrong rule.
2. **`_saveConstructionRule` sets `ordering: 0` unconditionally** on every insert/update, ignoring the ordering field from existing rows. This would silently collapse ordering on save.
3. **`resolveConstructionCell` passes `constructionRules` as both `constructionRules` and `allConstructionRules`** when called from `generateParadigm`. For POS-scoped resolution this is correct, but when a `CellFormReference` targets a cell with a construction rule in a *different* POS, the cross-POS reference will fall through silently rather than resolving — the code is correct per the spec scope, but the silent fallthrough warrants documentation or a guard.
4. **`suppressConstructionRuleId` column on `ParadigmCellOverrides` is wired in the DB schema but never read in the engine** — the suppression feature is plumbed but has no effect, which may be intentional (deferred), but leaves dead column that users cannot leverage.

## Warnings

### WR-01: Construction rule click-to-edit lookup is name-based, not id-based

**File:** `lib/features/grammar/presentation/paradigm_viewer/paradigm_table_widget.dart:720-726`
**Issue:** When a `ParadigmConstructionFilled` cell is tapped in `ruleEditor` mode, the widget looks up the matching `ConstructionRule` by comparing `r.name == localCell.constructionName`. The `constructionName` field on `ParadigmConstructionFilled` is set to `winner.name` (the rule's name string). Rule names are not unique — the schema has no `UNIQUE` constraint on `construction_rules.name`. If two active construction rules share the same name (which is user-editable), the first match in the provider list is returned, and the dialog opens for the wrong rule without any error.

**Fix:** Store the winning rule's `id` on `ParadigmConstructionFilled` instead of (or alongside) its name. Then the click handler can look up by id, which is unique by definition.

In `paradigm_cell.dart`, add an `ruleId` field:
```dart
class ParadigmConstructionFilled extends ParadigmCell {
  ParadigmConstructionFilled({
    required this.tokens,
    required this.constructionName,
    required this.ruleId,  // add this
    String? form,
    String? phonemic,
  }) ...
```

In `paradigm_engine.dart` line 429-435, pass the winner id:
```dart
final result = ParadigmConstructionFilled(
  tokens: tokens,
  constructionName: winner.name,
  ruleId: winner.id,  // add this
);
```

In `paradigm_table_widget.dart` line 720-726, change the lookup to:
```dart
final matchingRule = constructionRules
    .where((r) => r.id == localCell.ruleId)
    .firstOrNull;
```

### WR-02: `_saveConstructionRule` unconditionally resets `ordering` to 0 on every update

**File:** `lib/features/morphology/presentation/rules/rule_editor/rule_editor_body.dart:317-330`
**Issue:** When updating an existing construction rule (`_editingConstructionRule != null`), the code constructs the `ConstructionRuleRow` with `ordering: _editingConstructionRule!.ordering` — which correctly preserves ordering. However, the companion used for insert (line 302-313) always writes `ordering: const Value(0)`. More critically, the update path at line 317 uses the hardcoded `ordering: _editingConstructionRule!.ordering` value, which is correct today. The actual bug is that the `ConstructionRulesCompanion` built for insert (line 302) uses `ordering: const Value(0)` unconditionally even for new rules where a non-zero ordering might be desired. This is a minor issue for inserts, but combined with the fact that the UI has no ordering control, all new rules will stack at ordering=0 and rely on insertion order for tie-breaking.

More specifically: the `isActive` field is hardcoded to `true` on every save (lines 307, 319). If the user toggled an existing rule inactive (via a hypothetical future toggle or direct DB edit), opening the edit dialog and saving would silently re-activate the rule.

**Fix:** Preserve `isActive` from the existing row on update:
```dart
final existingRow = db.ConstructionRuleRow(
  id: _editingConstructionRule!.id,
  name: name,
  isActive: _editingConstructionRule!.isActive,  // preserve, don't hardcode true
  ordering: _editingConstructionRule!.ordering,
  ...
);
```

### WR-03: `resolveConstructionCell` called with POS-scoped rules for both `constructionRules` and `allConstructionRules` — cross-cell references to other POS cells silently fall through

**File:** `lib/features/grammar/data/typology_providers.dart:370-390`
**Issue:** In `generateParadigm`, both `constructionRules` and `allConstructionRules` are passed the same POS-scoped list. Inside `resolveConstructionCell`, when a `CellFormReference` targets a cell that might belong to a different POS, `allConstructionRules` is used to look for a construction rule for that target. Because the list is POS-scoped, cross-POS references will always fall through to the inflectional chart result without any error or log — they silently resolve as if no construction rule existed for the referenced cell (line 401-408 in `paradigm_engine.dart`).

This is architecturally intentional (cross-POS references are out of scope) but the silent fallthrough could confuse users who author a cross-POS cell reference in the UI. The `CellFormReference` picker in `rule_editor_body.dart` only surfaces cells from the currently-selected POS (line 661-696), so cross-POS references cannot be created through the UI today — but the engine would silently ignore them if they appeared in DB.

**Fix (minimal):** Add a comment at the call site in `generateParadigm` (typology_providers.dart ~line 381) documenting that `allConstructionRules` is intentionally POS-scoped and why cross-POS refs fall through gracefully. No behavior change required since the UI prevents the scenario — the comment prevents future confusion:
```dart
// NOTE: allConstructionRules is scoped to this POS. Cross-POS
// CellFormReferences are not authored through the UI and fall through
// to the inflectional chart result (T-10.1-05 graceful handling).
allConstructionRules: constructionRules,
```

### WR-04: `suppressConstructionRuleId` is schema-wired but never read by the engine

**File:** `lib/db/app_database.dart:241-244`
**Issue:** `ParadigmCellOverrides.suppressConstructionRuleId` was added in v16 per the comment "suppresses this construction rule for this specific word/cell combination." However, no code in the engine or providers reads this column. `resolveConstructionCell` and `generateParadigm` do not accept override data at all — they have no path to check whether a specific lexeme+cell has a suppression. The column is a dead write: it can be stored in the DB but has zero effect on rendering.

This is likely intentional deferral, but the gap between what the column comment promises and what the engine delivers is a correctness risk if users or tests rely on it working.

**Fix:** Either (a) add a `// NOT YET IMPLEMENTED — deferred to follow-up` comment on the column, or (b) wire suppression into `computedInflectedParadigmProvider` so it passes suppressed rule ids into `resolveConstructionCell`. Minimal fix:
```dart
/// v16 — Phase 10.1 D-03. NOT YET IMPLEMENTED: stored but not yet
/// consulted by the engine. Deferred to a follow-up task.
IntColumn get suppressConstructionRuleId => integer().nullable()();
```

### IN-01: `_lookupPool` key generation is order-dependent relative to `grouped` map keys

**File:** `lib/features/grammar/presentation/paradigm_viewer/paradigm_table_widget.dart:431-438`
**Issue:** `_lookupPool` builds a lookup key as `combo.entries.map((e) => '${e.key}:${e.value}').join(',')` without sorting entries. The `grouped` map is produced by `lexemesByIntrinsicCombinationProvider` (not in scope for this review), which likely sorts its own keys the same way. If the two sides ever produce the same combo with entries in different insertion orders, lookups would return empty even when matches exist. The `featureSetKey` helper in `typology_providers.dart` always sorts entries — this helper does not.

**Fix:** Sort entries before joining, consistent with `featureSetKey`:
```dart
final keyStr = (combo.entries.toList()
    ..sort((a, b) => a.key.compareTo(b.key)))
    .map((e) => '${e.key}:${e.value}').join(',');
```

### IN-02: `_buildCyclePath` uses a `Set<String>` which has non-deterministic iteration order in Dart

**File:** `lib/features/grammar/domain/paradigm_engine.dart:502-505`
**Issue:** `_buildCyclePath` iterates `stack` (a `Set<String>`) directly. Dart's `Set` (specifically `LinkedHashSet`) preserves insertion order, so in practice the path string is stable. This is implicitly relying on insertion-order semantics that are guaranteed by `LinkedHashSet` but not by the `Set` interface. The code is correct today but fragile if the set type were ever changed to a non-insertion-order variant.

**Fix:** No immediate code change required — `LinkedHashSet` insertion order IS guaranteed by `dart:core`. Add a brief comment:
```dart
// `stack` is a LinkedHashSet (dart:core Set default) which preserves
// insertion order — so the path faithfully reflects the resolution chain.
final parts = [...stack, newKey].map((k) => 'Cell $k').toList();
```

### IN-03: Construction rule delete in `_ConstructionRuleCard` has no confirmation dialog

**File:** `lib/features/grammar/presentation/inflectional_rules/inflectional_rules_page.dart:207-213`
**Issue:** The delete icon in `_ConstructionRuleCard` calls `dao?.deleteRule(rule.id)` immediately on tap with no undo or confirmation. The comment "deletes immediately (no confirm)" acknowledges this. Other destructive operations in the codebase (e.g. lexeme delete) typically show a confirm dialog. A misclick permanently removes the rule and all its POS junction rows (CASCADE). Unlike morphological rules, there is no soft-delete or `isActive` toggle path used here.

**Fix:** Either add a brief confirmation dialog (`AlertDialog` with Confirm/Cancel), or add a snackbar undo action, consistent with how other destructive deletes are handled in the app:
```dart
onPressed: () async {
  final confirmed = await showDialog<bool>(
    context: context,
    builder: (_) => AlertDialog(
      title: const Text('Delete construction rule?'),
      content: Text('Delete "${rule.name}"? This cannot be undone.'),
      actions: [
        TextButton(onPressed: () => Navigator.pop(context, false), child: const Text('Cancel')),
        TextButton(onPressed: () => Navigator.pop(context, true), child: const Text('Delete')),
      ],
    ),
  );
  if (confirmed == true) {
    final dao = ref.read(constructionRuleDaoProvider);
    await dao?.deleteRule(rule.id);
  }
},
```
