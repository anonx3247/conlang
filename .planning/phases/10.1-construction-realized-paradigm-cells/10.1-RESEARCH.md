## Summary

Phase 10.1 bridges the existing paradigm engine (Phase 4) with the Phase 10 phrase constructions. It introduces construction rules as a new rule kind — POS-scoped and feature-bound like inflectional rules — that analytically realize paradigm cells via existing constructions. The word slot in the chosen construction resolves to either the base form or the output of another paradigm cell, composing with any inflectional rules that also fire on the same cell.

The implementation touches four layers: (1) the domain model (`ParadigmCell` sealed hierarchy + a new `ConstructionRule` model), (2) the paradigm engine (`computeParadigmCell` must run a construction resolution pass after the inflectional chain), (3) the data layer (new table + v16 migration), and (4) the rule editor UI (`RuleEditorDialog` gains a construction variant). Cycle detection is a discrete named state (`ParadigmUnresolvable`) handled in the engine, not in the UI.

The codebase is well-structured for this extension. `computeParadigmCell` is a pure function with a sealed return type — adding new variants is compile-time safe. The `FeatureBindings` JSON format, `InflectionalRulePOS` junction pattern, and `ParadigmCellOverrideDao` `(lexemeId, featureSetJson)` keying are all directly reusable.

**Primary recommendation:** Use a separate `ConstructionRules` table (not a new `kind` on `MorphologicalRules`) for storage — the word-slot designation and form-reference columns are structurally distinct from the DSL `source` column on `MorphologicalRules`, and co-locating them would require multiple nullable columns and complicate every query that reads rules. Use a separate `ConstructionRulePOS` junction table following the `InflectionalRulePOS` pattern for multi-POS scoping.

### Pattern 1: Separate ConstructionRules Table (RECOMMENDED over kind extension)

**What:** A new `ConstructionRules` table holds construction-specific columns that have no analog in `MorphologicalRules`. A `ConstructionRulePOS` junction mirrors `InflectionalRulePOS`.

**Why separate table over `kind='construction'` on MorphologicalRules:**
- `MorphologicalRules.source` is a DSL string — construction rules have no DSL source
- Three new nullable columns (`construction_id`, `word_slot_id`, `form_reference_json`) would be required on MorphologicalRules with a `kind` discriminant, bloating every rule query
- `InflectionalRulePOS` already shows the junction pattern works cleanly — mirroring it for construction rules gives consistent query patterns
- [VERIFIED: codebase] `MorphologicalRules` already has 10 columns; adding 3 more `nullable()` columns for one rule kind is an anti-pattern

**Schema proposal (Claude's discretion — D-12):**

```sql
-- v16 migration
CREATE TABLE construction_rules (
  id INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  is_active INTEGER NOT NULL DEFAULT 1,
  ordering INTEGER NOT NULL DEFAULT 0,
  construction_id INTEGER NOT NULL REFERENCES phrase_constructions(id) ON DELETE CASCADE,
  word_slot_id INTEGER NOT NULL REFERENCES construction_slots(id) ON DELETE CASCADE,
  -- JSON: null = base form, otherwise {"kind":"cell","featureSet":{"dimId":levelId,...}}
  form_reference_json TEXT NOT NULL DEFAULT 'null',
  -- Reuses FeatureBindingsConverter JSON for dim bindings (pos list + dims map)
  feature_bindings TEXT NOT NULL DEFAULT '{}'
);

CREATE TABLE construction_rule_pos (
  rule_id INTEGER NOT NULL REFERENCES construction_rules(id) ON DELETE CASCADE,
  pos_id INTEGER NOT NULL REFERENCES parts_of_speech(id) ON DELETE CASCADE,
  PRIMARY KEY (rule_id, pos_id)
);
```

**Dart table definitions follow the same Drift patterns as `PhraseConstructions` + `ConstructionSlots`.**

### Pattern 2: Per-Word Construction Suppression (Claude's discretion — D-03)

**Decision:** Extend `ParadigmCellOverrides` with an optional `suppressConstructionRuleId` column rather than a separate join table.

**Rationale:**
- The override dialog already exists at `cell_override_dialog.dart` and is keyed by `(lexemeId, featureSetJson)`
- Per-word construction suppression is per-cell, not per-rule globally — the same key structure applies
- A new `INT NULL suppress_construction_rule_id` on `ParadigmCellOverrides` carries: null = no suppression, non-null = suppress that construction rule for this cell
- Alternative (new join table) is more normalized but adds another DAO, provider, and migration step for what amounts to a single int column
- [ASSUMED] Adding a nullable column to `ParadigmCellOverrides` via `addColumn` in v16 migration is straightforward in Drift with the `withDefault(const Constant(null))` pattern

### Pattern 3: Construction Rule Resolution in paradigm_engine.dart

**What:** A post-inflectional-chain step that wraps `ParadigmFilled` (or bare root) in a construction.

**Integration point in `computeParadigmCell`:**

```dart
// Source: codebase analysis of paradigm_engine.dart
// After the existing inflectional chain loop produces `working` (inflected form):

// 1. Run inflectional chain as today → produces ParadigmFilled or early return
// 2. Check if a construction rule binds the target featureSet for this POS
// 3. If yes:
//    a. Resolve word slot form (base or referenced cell — with cycle guard)
//    b. Assemble ConstructionToken list from construction slots
//    c. Return ParadigmConstructionFilled instead of ParadigmFilled
// 4. Apply rewrite pipeline to the assembled form (phonemic + phonetic split,
//    same D-112 invariant)
```

**Cycle detection algorithm (DFS, iterative):**

```dart
// Source: codebase analysis — D-09 requirement
Set<String> resolving = {};  // featureSet keys currently on the stack

ParadigmCell resolveCell(FeatureSet target, ...) {
  final key = featureSetKey(target);
  if (resolving.contains(key)) {
    return ParadigmUnresolvable(cyclePath: _buildCyclePath(...));
  }
  resolving.add(key);
  final result = _computeWithConstruction(target, ...);
  resolving.remove(key);
  return result;
}
```

The cycle detector must be threaded as a parameter (or a mutable set passed by reference) since `computeParadigmCell` is called recursively when resolving cell cross-references.

### Pattern 4: ParadigmConstructionFilled — Token List Model

**What:** The `ParadigmConstructionFilled` variant holds a `List<ConstructionToken>` rather than a plain string, so the renderer can apply violation highlighting to the composed output.

**Token struct:**
```dart
// Analogous to InlineSpan approach used in construction_preview.dart
sealed class ConstructionToken {}
class ParticleToken extends ConstructionToken {
  final String ipa;   // particle's raw IPA (from closed-class lexeme)
  final String? romanization;
}
class WordSlotToken extends ConstructionToken {
  final String ipa;   // resolved form IPA
  final String phonemic;  // pre-rewrite form for romanize() — D-112 invariant
}
```

The assembled IPA for the cell = space-joined token IPA strings. The `phonemic` for romanization = space-joined phonemic fields. Violation highlighting runs on the full assembled IPA (same as existing `_FilledCell` pattern).

### Pattern 5: RuleEditorDialog Construction Variant

**What:** A new `RuleKind.construction` variant added to the existing `RuleKind` enum. The `RuleEditorDialog` receives `kind: RuleKind.construction` and `RuleEditorBody` switches rendering.

**How:** The `RuleEditorBody._RuleEditorBodyState` already stores `_featureBindings` and `_inflectionalPosSet` — construction rules reuse these identically. The only swap is the body below the POS/binding chips: instead of `BranchEditor` (DSL operations), show the three-picker form (construction → word slot → form reference).

**Key: `RuleEditorDialog` receives an optional `existingConstructionRule` parameter alongside the existing `existing` parameter for `MorphologicalRule`. The dialog routing in `_ParadigmCellWidget.openDialog()` already dispatches on cell type — add a `ParadigmConstructionFilled` branch that opens with the construction rule loaded.**

### Anti-Patterns to Avoid

- **Wrapping computeParadigmCell externally:** The construction resolution must be integrated inside `computeParadigmCell` (or called from `generateParadigm` after each cell). Do NOT wrap it at the provider layer — that loses access to the cycle detection stack which must span the entire recursive resolution tree.
- **Resolving the full chart before cycle detection:** Cycle detection requires knowing what cells are being resolved on the current call stack. Pre-building the full chart then post-processing for cycles will not detect mutual cross-cell references correctly.
- **Storing assembled string instead of token list:** Storing the construction output as a plain IPA string loses the ability to apply violation highlighting to sub-spans. Store tokens.
- **Reusing `MorphologicalRules.source` = "":** An empty DSL source would cause `InflectionalRule.fromDbRow` assert failures if construction rows were ever accidentally fed to the inflectional path. Keep construction rules in their own table.
- **Using `kind='construction'` on `MorphologicalRules`:** See Pattern 1 rationale above.

## Common Pitfalls

### Pitfall 1: Cycle Detection Scope Too Narrow
**What goes wrong:** Cycle detection only catches direct self-loops (A→A) but misses indirect cycles (A→B→A).
**Why it happens:** Checking `target == selfFeatureSet` in `computeParadigmCell` only catches A→A. B→A is only detectable if the resolution stack is threaded across all recursive calls.
**How to avoid:** Pass a `Set<String> resolvingStack` parameter through the entire resolution call chain. Add `featureSetKey(target)` to the set before recursing, remove it after. Return `ParadigmUnresolvable` immediately when the target is already in the set.
**Warning signs:** A test with A→B→A resolving correctly instead of returning `ParadigmUnresolvable`.

### Pitfall 2: computeParadigmCell Signature Change Breaks All Callers
**What goes wrong:** Adding `constructionRules` and `closedClassWords` parameters to `computeParadigmCell` causes compile errors at all 5+ existing call sites.
**Why it happens:** The function is called from `generateParadigm`, tests, and directly in the paradigm engine.
**How to avoid:** Make the new parameters optional with `const []` defaults. [VERIFIED: codebase] The existing `rewriteRules`, `markers`, `lexemeIntrinsicLevels`, `dimensionIntrinsicFlags` parameters all use this pattern.
**Warning signs:** `dart analyze` errors after adding the parameter before updating callers.

### Pitfall 3: D-112 Phonemic/Form Invariant Lost in Token Assembly
**What goes wrong:** The assembled construction output uses `form` (post-rewrite) everywhere, so `romanize(form)` leaks rewrite-pipeline artifacts into the romanization line.
**Why it happens:** `ParadigmFilled.form` is the post-rewrite phonetic; `ParadigmFilled.phonemic` is the pre-rewrite form. Construction assembly must track both through each token.
**How to avoid:** `WordSlotToken` must carry both `ipa` (phonetic) and `phonemic` fields. The renderer composes romanization from `phonemic` fields, IPA display from `ipa` fields.
**Warning signs:** Romanization of a construction cell shows `cazana` instead of `casana` (same symptom that triggered D-112 in plan 04-17).

### Pitfall 4: Sealed Switch Exhaustion in paradigm_table_widget.dart
**What goes wrong:** Adding `ParadigmConstructionFilled` and `ParadigmUnresolvable` to the sealed hierarchy causes compile errors in every `switch (cell)` in `paradigm_table_widget.dart`.
**Why it happens:** `paradigm_cell.dart` is a sealed class — all subtypes must be handled exhaustively. [VERIFIED: codebase] Current switch at line ~754 handles `null`, `ParadigmUncovered`, `ParadigmAmbiguous`, `ParadigmFilled`, `ParadigmUnmarked`.
**How to avoid:** Add the new variants to the sealed class first; the compiler will immediately flag all switch statements that need updating. Fix all call sites before running tests.
**Warning signs:** `The type 'ParadigmConstructionFilled' is not exhaustively matched` compile errors.

### Pitfall 5: Construction Rule Lookup in Engine Requires Sync Data
**What goes wrong:** `computeParadigmCell` is a pure synchronous function but looking up construction rules from the DB is async.
**Why it happens:** `generateParadigm` and `computeParadigmCell` are synchronous pure functions — they receive pre-loaded data as parameters. Adding an async DB call inside them breaks the synchronous contract.
**How to avoid:** Construction rules must be loaded in the Riverpod provider (`computedInflectedParadigmProvider`) alongside the existing `rules`, `markers`, `rewriteRules` — then passed in as a parameter. [VERIFIED: codebase] `computedInflectedParadigmProvider` already loads `rules`, `inventory`, `rewriteRules`, `markers` before calling `generateParadigm`.
**Warning signs:** `await` inside `computeParadigmCell` or `generateParadigm`.

### Pitfall 6: ConstructionRule Provider Pattern — Riverpod Codegen Forbidden
**What goes wrong:** Using `@riverpod` codegen annotation for construction rule providers breaks Drift integration.
**Why it happens:** Per STATE 01-05 (confirmed in codebase comments): "riverpod_generator 3.x cannot resolve Drift part-file types at codegen time, so grammar-scoped providers that traffic in Drift-generated classes must be hand-written."
**How to avoid:** Write construction rule providers as plain `Provider`, `StreamProvider`, and `StreamProvider.family` — same as `construction_providers.dart`. [VERIFIED: codebase]
**Warning signs:** `@riverpod` annotation on any file that imports `app_database.dart`.

### Pitfall 7: beforeOpen Safety Net Missing for New Tables
**What goes wrong:** A hot-restart during development bumps `user_version` without completing the migration, leaving the new tables absent.
**Why it happens:** Drift's `user_version` is set before `onUpgrade` completes on hot-restart.
**How to avoid:** Add `CREATE TABLE IF NOT EXISTS construction_rules (...)` and `CREATE TABLE IF NOT EXISTS construction_rule_pos (...)` safety-net statements to `beforeOpen`. [VERIFIED: codebase] Every prior table has a safety-net entry.
**Warning signs:** `no such table: construction_rules` errors on hot-restart during development.

## Open Questions

1. **Where does the construction engine resolution live — inside `computeParadigmCell` or as a separate post-pass in `generateParadigm`?**
   - What we know: `computeParadigmCell` is called per-cell and is currently synchronous and pure. Cell cross-references (D-05/D-06) require resolving OTHER cells during resolution of the current cell, which means the cycle detector must span multiple `computeParadigmCell` calls.
   - What's unclear: Whether to thread the cycle stack through `computeParadigmCell` parameters, or hoist all construction resolution to `generateParadigm` with a separate resolution step.
   - Recommendation: A separate `resolveConstructionCell` function called from `generateParadigm` after the full inflectional chart is computed is simpler: resolve all non-cross-reference cells first, then resolve cross-reference cells using the already-computed chart, detecting cycles by checking if the referenced cell is in the "currently resolving" set. This avoids modifying `computeParadigmCell`'s signature for the recursive case.

2. **Should the construction rule per-word suppression be stored on `ParadigmCellOverrides` or a new `ConstructionCellSuppression` table?**
   - What we know: D-03 says "planner to decide exact shape". `ParadigmCellOverrides` is keyed by `(lexemeId, featureSetJson)` — same key needed for suppression.
   - What's unclear: Whether suppression should be independent of or co-located with form overrides.
   - Recommendation: Add a nullable `suppressConstructionRuleId INT` column to `ParadigmCellOverrides`. A row with `overrideIpa=''` and `suppressConstructionRuleId=X` would mean "suppress construction rule X for this cell, show the morphological result instead". Keep it simple — this avoids a new table, DAO, and migration step.

This phase is a desktop Flutter app, offline-only, single-user, no network calls, no authentication surface. ASVS categories V2/V3/V4/V6 do not apply. V5 (input validation) applies at the boundary where user-supplied construction rule data is stored.

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no | not applicable |
| V3 Session Management | no | not applicable |
| V4 Access Control | no | not applicable |
| V5 Input Validation | yes | Drift typed columns + FeatureBindingsConverter JSON parsing (defense in depth: malformed JSON decodes to empty, not crash) |
| V6 Cryptography | no | not applicable |

No new threat vectors introduced. Construction rule data is user-generated, single-user, stored locally in SQLite with Drift's parameterized queries throughout.
