## Critical Issues

### CR-01: Force-unwrap of nullable `ZipEncoder.encode()` result will crash on failure

**File:** `lib/features/lexicon/data/anki_exporter.dart:61`
**Issue:** `ZipEncoder().encode(archive)!` force-unwraps a nullable `List<int>?`. The `encode` method can return `null` (e.g., empty archive edge case or encoder error). A null result throws a `Null check operator used on a null value` at runtime, bypassing the `finally` block that disposes the DB and crashes the export without a user-visible error message.

**Fix:**
```dart
final encoded = ZipEncoder().encode(archive);
if (encoded == null) {
  throw StateError('ZipEncoder.encode returned null — archive may be empty or malformed.');
}
return Uint8List.fromList(encoded);
```

### WR-01: Table column labels are misaligned with sort keys and cell content

**File:** `lib/features/lexicon/presentation/dictionary/word_list_panel.dart:515-585`
**Issue:** The `DataTable` column headers and sort logic are inconsistent with cell rendering order:
- Column 0 header: `'Word'` — renders `lexeme.ipa` — sorts on `a.ipa` (sort key matches cell, but label is wrong)
- Column 1 header: `'IPA'` — renders `lexeme.romanization` — sorts on `a.romanization` (label says "IPA" but content and sort key are romanization)

When a user clicks the "IPA" column header, the list sorts by romanization, not IPA. The visual sort indicator appears on the "IPA" column while romanization values are being ordered. This is a visible correctness bug for any user with both IPA and romanization populated.

**Fix:** Rename column headers to match cell content:
```dart
// Column 0 — shows lexeme.ipa
DataColumn(label: const Text('IPA'), onSort: ...),
// Column 1 — shows lexeme.romanization
DataColumn(label: const Text('Romanization'), onSort: ...),
// Column 2 — unchanged: 'POS'
// Column 3 — unchanged: 'Meaning'
```

### WR-02: `ref.watch(allLexemeListProvider)` called inside `ListView.builder` itemBuilder

**File:** `lib/features/lexicon/presentation/dictionary/word_list_panel.dart:353`
**Issue:** `ref.watch(allLexemeListProvider)` is called inside the per-item closure of `ListView.builder`. This registers a separate provider subscription for every visible list item. When `allLexemeListProvider` emits a new value, every item triggers a rebuild independently rather than the whole list rebuilding once. In practice this causes redundant rebuilds and can lead to stale data being displayed for items whose rebuilds land in different frames. The derived-match count logic also re-executes a `.where` over the full `allLexemes` list per item, making the total work O(n²) for n items — but more importantly, this is a correctness issue because the subscription count is unbounded and dependent on scroll position.

**Fix:** Hoist the watch to the top of `_buildListView` (or to `build`) and pass the resolved list down:
```dart
Widget _buildListView(BuildContext context, List<dynamic> lexemes, Set<int> derivedMatches) {
  // Hoist outside itemBuilder — single subscription, resolved once per rebuild.
  final allLexemes = ref.watch(allLexemeListProvider).asData?.value ?? [];
  final violations = ref.watch(lexemeViolationsProvider);

  return ListView.builder(
    itemCount: lexemes.length,
    itemBuilder: (context, index) {
      final lexeme = lexemes[index];
      // Use captured allLexemes — no ref.watch inside itemBuilder
      final rootIdStr = lexeme.id.toString();
      final derivedMatchCount = derivedMatches
          .where((id) => allLexemes.any((l) => l.id == id && l.rootId == rootIdStr))
          .length;
      ...
    },
  );
}
```

### WR-03: `_shortPlace` crashes on empty string input

**File:** `lib/features/phonology/presentation/inventory/inventory_page.dart:61`
**Issue:** The fallback `p.substring(0, 2)` in `_shortPlace` throws `RangeError` if `p` is an empty string (or a single-character string). A phoneme with a blank `place` field stored in the DB (possible via direct DB edit or migration gap) would crash the entire consonant grid render.

**Fix:**
```dart
String _shortPlace(String p) {
  const m = { /* existing map */ };
  if (m.containsKey(p)) return m[p]!;
  if (p.length < 2) return p; // guard against short/empty strings
  return p.substring(0, 2);
}
```

### WR-04: `_revealInFinder` is fire-and-forget — unhandled async

**File:** `lib/features/lexicon/presentation/dictionary/dictionary_page.dart:241-251`
**Issue:** `Process.run(...)` is async and returns a `Future<ProcessResult>`. The calls are not `await`ed and the returned futures are silently discarded. While this is documented as "best effort", unawaited futures suppress errors and the linter (`unawaited_futures` lint rule) will flag this. More practically, if the export snackbar dismisses and the widget is unmounted before the process completes, any error is lost with no recourse.

**Fix:** Either explicitly discard with `unawaited()` from `package:meta`, or suppress with a comment that acknowledges intent:
```dart
void _revealInFinder(String dirPath) {
  try {
    if (Platform.isMacOS) {
      unawaited(Process.run('open', [dirPath])); // intentionally fire-and-forget
    } else if (Platform.isLinux) {
      unawaited(Process.run('xdg-open', [dirPath]));
    } else if (Platform.isWindows) {
      unawaited(Process.run('explorer', [dirPath]));
    }
  } catch (_) {}
}
```

### WR-05: `noteId` uniqueness degrades when `entries.length > 1000` within the same second

**File:** `lib/features/lexicon/data/anki_exporter.dart:225`
**Issue:** `noteId = now * 1000 + i` where `now` is seconds since epoch and `i` is the index. The formula allocates only 1000 unique IDs per second (`i` uses 0–999 range before overflowing into the next second's space). If `entries.length > 1000`, `noteId` values collide (e.g., `i=1000` produces the same value as `i=0` at `now+1`), causing `INSERT INTO notes` to fail with a PRIMARY KEY constraint violation and aborting the entire export. Realistic lexicons can exceed 1000 words.

**Fix:** Use a wider multiplier or milliseconds:
```dart
final nowMs = DateTime.now().millisecondsSinceEpoch;
final noteId = nowMs * 10000 + i; // supports up to 10,000 entries per millisecond
```
Or simply use `i` as the primary ID since all notes are inserted in a single transaction:
```dart
final noteId = i + 1; // simple sequential ID; unique within this export
```

### IN-01: `_csum` comment documents a different algorithm than what is implemented

**File:** `lib/features/lexicon/data/anki_exporter.dart:302-303`
**Issue:** The doc comment states "Anki uses SHA1" and the inline comment on line 303 says "We implement a compatible djb2 checksum". The method name says "compatible djb2 checksum within 32-bit range", but Anki's actual `csum` field uses the first 8 hex digits of SHA1. Using djb2 instead of SHA1 means the `csum` will not match what Anki would compute for the same field, which can cause duplicate-detection mismatches when importing the same deck twice. This is not a crash bug but a data-correctness gap worth fixing if round-trip import fidelity matters.

**Fix:** Implement SHA1 to match Anki's algorithm exactly, or update the comment to clearly state that the checksum intentionally diverges from Anki's specification and explain the accepted trade-off.
