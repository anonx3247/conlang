## Decisions Made

- **Path B for Test 3 (cluster-skip) — driven by parser probe** — The plan's `<read_first>` block mandated running `parseRewriteRule('st -> ʃt / #_')` as a scratch test before writing Test 3, with the result choosing between Path A (parser-constructed fixture) and Path B (raw constructor). Probe result: `isValid=true, inputLen=1, slot[0].literalPhoneme='st'`. The parser coalesces consecutive IPA characters into a single multi-char literal — this is consistent with how `tokenizeIpa` matches longest-first, but it means a parser-constructed fixture CANNOT have `input.length == 2`. Path B (raw `PhonologicalRewriteRule(input: [Slot(literalPhoneme: 's'), Slot(literalPhoneme: 't')], ...)`) was therefore the only viable path. Documented at the top of Test 3 with a one-line comment per the plan's auditability requirement.
- **Equality on output alone, not (output, ruleSource)** — Dedup semantics per D-12 say "one realization per surface form regardless of which rule produced it". Including `ruleSource` in equality would mean two rules producing the same output would count as two distinct realizations, defeating the dedup point. The `AllophoneRealization equality is based on output only (for dedup)` test locks this contract against future regression. A consequence is that `ruleSource` is effectively a "last-write-wins pointer" when dedup happens — the first rule to produce a given output wins, and subsequent rules' sources are discarded. This is acceptable because D-17 specifies ruleSource is "supplementary tooltip info", not primary display data, and Plan 04 will show the first rule's source when multiple rules produce the same realization.
- **Feature-bundle detection via string shape, not via parser field** — The `PhonologicalRewriteRule.output` field stores the RHS as a raw string per the existing Phase 1 design (applying the transformation is Phase 2 work). Rather than extending the parser to expose an `isFeatureBundle` field, `computeAllophones` sniffs the string shape (`startsWith('[') && endsWith(']') && length >= 2`). This keeps the change scoped to Plan 03's module and avoids touching the Phase 1 parser. The length>=2 guard prevents false positives on degenerate outputs like `[` or `]` alone.
- **Narrow `show` imports** — Imports use `show resolvePhonemeClass` and `show PhonemeInventory` to make the allophone module's dependencies explicit at the import line. This is a small documentation-in-code win: a reader opening the file immediately sees which symbols are being consumed without navigating to the target modules.
- **Short-circuit on empty inputs in the provider** — When `rules.isEmpty || phonemes.isEmpty`, the provider returns `const {}` immediately instead of running the per-phoneme loop. This is a micro-optimization with clear semantic intent: no work to do, no allocation required. The `const {}` literal is fully interned and re-used on every call.
- **`error: (_, _)` handles the AsyncValue error case** — The `_, _` pattern (two ignored positional params) matches `allPhonemesProvider`'s `AsyncError` shape. On a stream error, we treat it the same as "no phonemes loaded" and return `const {}` — defensive degradation matching the rest of the phonology provider family.
- **No mocking-based provider test** — The plan explicitly documented why: `allophoneMapProvider` is composition of already-tested pieces, and mocking three providers (`parsedRewriteRulesProvider`, `phonemeInventoryProvider`, `allPhonemesProvider`) to unit-test the composition would duplicate `computeAllophones` coverage with zero additional signal. Plan 04's widget tests, which will use `ProviderScope` overrides to inject fake phonemes and rules, will exercise the full chain end-to-end.
- **Parser-probe scratch file deleted after use** — The probe lived in `test/phonology/_probe_cluster.dart` and was removed immediately after capturing its findings in the main test file's header comment. Keeping it in-tree would pollute the test suite with `print`-based assertions that aren't real tests.

## Parser Gotchas Discovered

Three fixture-construction notes worth preserving for future test authors in this subsystem:

1. **Multi-character literals coalesce.** `parseRewriteRule('st -> ʃt / #_')` returns a SINGLE literal slot with `literalPhoneme='st'`, not two single-character slots. This is consistent with the IPA tokenizer's longest-first matching behavior but means the parser cannot be used to construct multi-segment-input fixtures. For cluster rules, use the raw `PhonologicalRewriteRule` constructor with a hand-built `List<Slot>` of length 2+.

2. **Single-letter uppercase inputs are class references, not literals.** `parseRewriteRule('S -> b / V_V')` returns `input[0].classReference='S'` (with `literalPhoneme=null`), NOT `input[0].literalPhoneme='S'`. The parser routes all uppercase single-letter inputs through the class-reference path. This means `S` goes through `resolvePhonemeClass('S', inventory)` → Plan 02's alias path → `defaultNaturalClassAliases['S']` → the default stop list. For literal single-letter inputs, lowercase letters work (e.g. `s -> ʃ`). Uppercase literals would require either a quoted-literal syntax (not currently supported) or a raw constructor fixture.

3. **Bracket-class references work as expected.** `parseRewriteRule('[stop] -> b / V_V')` returns `input[0].classReference='stop'` (lowercase) and `output='b'`. The bracket notation always routes to the class-reference path regardless of case inside the brackets. `V -> [+nasal] / _n` similarly parses with `output='[+nasal]'` preserved verbatim as a string, and the feature-bundle detection in `computeAllophones` catches it via the `[...]` shape.
