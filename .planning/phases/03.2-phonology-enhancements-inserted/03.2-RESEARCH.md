# Phase 3.2: Phonology Enhancements - Research

**Researched:** 2026-04-10
**Domain:** Flutter/Dart phonology UI + DSL class resolution + descriptive allophone listing
**Confidence:** HIGH (codebase grounded — every claim verified against actual files)

## Summary

Phase 3.2 ships two tightly-scoped phonology features on top of an already-stable Phase 3.1 codebase: (1) a hardcoded catalog of nine predefined natural classes that resolve transparently in the existing DSL, and (2) a contextual allophone viewer that lists realizations from existing rewrite rules in two surface points (the phoneme edit dialog and an Alt-held inline annotation in the inventory grids).

The good news: the parser, the DSL data model, the rewrite-rule storage, the Alt-key keyboard listener, and the phoneme dialog all already exist and work. No schema migration is needed and no new petitparser grammar is required. The work is integration plumbing — extending one provider, adding one pure-function module, and wiring two existing widgets.

The single most important finding contradicts the integration-point claim in CONTEXT.md D-05: **`NaturalClassDao.resolveClass` is dead code**. It has zero callers in `lib/`. The runtime resolution path goes through `phonotactic_providers.dart::_buildInventory` → `PhonemeInventory.naturalClasses` (a `Map<String, List<String>>` snapshot) → `WordGenerator._resolveClass` and `morphology_engine::resolvePhonemeClass`. The defaults must be injected at the snapshot-build site, not at the DAO method, otherwise the DSL will not see them. This is the load-bearing decision the planner must internalize.

**Primary recommendation:** Inject default classes inside `_buildInventory` in `phonotactic_providers.dart` by merging a `defaultNaturalClasses` const map with the user's classes (user wins on collision per D-06). Treat D-05 as conceptually correct (resolution is the integration point) but redirect the implementation from `NaturalClassDao.resolveClass` to `_buildInventory`. Optionally also extend `resolveClass` for symmetry / future use.

## Critical Findings (read these first)

### F-1: `NaturalClassDao.resolveClass` is dead code; the real integration point is `_buildInventory` (HIGH confidence)

**Verified by:** `Grep -n '\.resolveClass\('` returns zero matches under `lib/`. Only references are in planning docs and the DAO definition itself.

The runtime path that consumes natural classes is:

```
Phoneme/NaturalClass DB rows
  → consonantListProvider / vowelListProvider / naturalClassListProvider
  → phonemeInventoryProvider          [phonotactic_providers.dart:160]
  → _buildInventory(...)              [phonotactic_providers.dart:180]
  → PhonemeInventory.naturalClasses   (Map<String, List<String>> snapshot, lowercase keys)
  → consumed by:
      - WordGenerator._resolveClass            [word_generator.dart:213]
      - morphology_engine.resolvePhonemeClass  [morphology_engine.dart:71]
```

Both `_resolveClass` implementations look up `inventory.naturalClasses[classRef.toLowerCase()]`. They never call any DAO. **Adding defaults to `NaturalClassDao.resolveClass` would be invisible to every actual consumer.**

**Implication for planner:**
- **Primary fix:** Modify `_buildInventory` in `lib/features/phonology/data/phonotactic_providers.dart` to merge `defaultNaturalClasses` with the user's classes. User classes win on key collision (D-06). The merge must happen on the lowercased key (since the existing code stores `cls.name.toLowerCase()`).
- **Symmetric fix (recommended):** Also extend `NaturalClassDao.resolveClass` to fall back to defaults — even though it's currently unused, it is a logical resolution point and a future caller (e.g. a future autocomplete UI) will expect it to work. This is cheap and matches the user's mental model in D-05.
- **Aliases (D-09):** Single-letter aliases (`S`, `L`, `R`, `F`, `N`) need a separate registration. The current `_resolveClass` lowercases the input — `S` becomes `s`, which would shadow a user phoneme `/s/` if naively keyed. See finding F-2.

This finding does **not** invalidate D-05 — it refines where the implementation lives. The intent ("one load-bearing integration point so all consumers see defaults transparently") is preserved by patching `_buildInventory`.

### F-2: Single-letter alias collision risk with literal phonemes (HIGH confidence)

**Verified by:** Reading `phonotactic_dsl.dart:171–188` (`_segmentParser`) and `morphology_engine.dart:71–87` (`resolvePhonemeClass`).

The parser tries `[bracketName]` first, then a single uppercase letter (`uppercase().flatten()`), then any other character as a literal. So:

| DSL input | Parsed slot |
|-----------|-------------|
| `[stop]` | `Slot(classReference: 'stop')` |
| `[Stop]` | `Slot(classReference: 'Stop')` |
| `[S]` | `Slot(classReference: 'S')` |
| `S` (bare) | `Slot(classReference: 'S')` (single uppercase shorthand) |
| `s` (bare) | `Slot(literalPhoneme: 's')` (lowercase falls through to literal) |
| `[s]` | `Slot(classReference: 's')` |

The lookup function then does `classRef.toLowerCase()` and reads `inventory.naturalClasses[key]`. So if we register a default under the lowercased key `s`, then `[S]`, `[s]`, `S` (bare), and `[Stop]→stop` all collapse to lookups on the same map. The collision risk:

1. **Bracketed literals look like classes.** A user writing `[s]` thinks they're referencing the literal phoneme `/s/`, but the parser turns this into a class reference and the resolver returns the entire Stop class. **This is pre-existing behavior, not a regression — but adding a default class under key `s` worsens the surprise because now `[s]` will silently expand to all stops instead of returning empty.**
2. **Single-letter aliases (D-09) want case-sensitivity.** The current `_resolveClass` is case-insensitive (`toLowerCase` first, then exact-case fallback). To make `S` mean "Stop" but allow `s` to remain a literal, the alias map must be checked **before** the toLowerCase fallback, with exact-case key `S`.

**Recommended resolution (planner decision):**
- Store the default catalog with **two key sets**: full name (lowercased: `stop`, `nasal`, `fricative`, …) and single-letter alias (uppercase: `S`, `N`, `F`, `L`, `R`).
- Modify `_resolveClass` / `resolvePhonemeClass` (and the new `_buildInventory` merge) to check the alias map **with exact case** before lowercasing. If exact-case match fails, fall through to the existing lowercased-name lookup. This preserves backward compatibility (lowercase `[stop]` still works because it's stored as `stop` in the lowercased map).
- Document the existing `[s]→class` ambiguity as a pre-existing parser quirk; not a Phase 3.2 fix. Add a note to the natural class editor or DSL docs warning that single-character bracketed names are interpreted as class references.
- Reserved aliases `S`, `N`, `F`, `L`, `R` join `C` and `V` as single-letter shorthands. Add a defensive validator in `NaturalClassEditor` so users cannot create user-defined classes with these reserved single-letter names (currently the validator only blocks `C` and `V` — see `natural_class_editor.dart:113`).

### F-3: Default class IPA member lists — verification against IPA chart conventions (MEDIUM-HIGH confidence)

**Verified by:** Cross-referencing CONTEXT.md D-07 against the standard IPA chart and `IpaSound` static data in `ipa_data.dart` (which defines the project's enum-driven set of pulmonic and non-pulmonic consonants and vowels).

The proposed lists are sound for a default catalog. Notes and minor recommendations:

| Class | Status | Notes |
|-------|--------|-------|
| **Stop (S)** | Verified — accept as-is | Includes ʔ which is a stop phonologically; some sources omit ʔ from "stops" but it's standard to include it. The list covers bilabial → glottal across both voicings. `[CITED: IPA chart 2020]` |
| **Nasal (N)** | Verified — accept as-is | All standard pulmonic nasals from m to ɴ. `[CITED: IPA chart 2020]` |
| **Fricative (F)** | Verified — accept as-is | Comprehensive. Includes both ʁ (uvular fricative) and lateral fricatives are NOT included (ɬ ɮ omitted). **Recommend adding ɬ and ɮ** (lateral fricatives) for completeness — they're part of the IPA fricative row. `[CITED: IPA chart 2020]` |
| **Liquid (L)** | Verified with caveat | Includes ʁ which is also in Fricative. Cross-membership is fine and expected (the user explicitly noted this). The "liquid" category is informal; this union approach is the standard descriptive convention. `[ASSUMED]` for the exact set — no canonical list exists, but this is reasonable. |
| **Rhotic (R)** | Verified — accept as-is | The r-family is well-defined: trills (r, ʀ), taps/flaps (ɾ, ɽ), approximants (ɹ, ɻ), uvular fricative ʁ (when functioning rhotically). `[CITED: Ladefoged & Maddieson 1996]` |
| **Obstruent** | Verified — derive at module load | Stop ∪ Fricative ∪ Affricate. Best represented as a const that references the other three lists rather than a duplicated literal. |
| **Sonorant** | Verified with caveat | CONTEXT.md notes "consonant-focused, no vowels." This matches some textbooks but contradicts strict featural phonology (where vowels ARE [+sonorant]). **Recommend documenting this as a deliberate UX choice** in the const file's doc comment so future contributors don't "fix" it. `[ASSUMED]` — common convention but contested. |
| **Approximant** | Verified — accept as-is | j, w, ɥ, ɰ, ʋ, plus ɹ, ɻ (rhotic approximants), plus l, ɭ, ʎ, ʟ (lateral approximants). Good. `[CITED: IPA chart 2020]` |
| **Affricate** | Verified with caveat | Uses the IPA tie-bar form (`t͡s`, `t͡ʃ`, etc.). **Critical:** the project's existing tokenizer uses longest-match-first (`word_generator.dart:241`), so multi-codepoint affricates with U+0361 will tokenize correctly only if they're in `inventory.consonants` or in another natural class. **For out-of-inventory affricates, the tokenizer never sees them, so they can never appear as input to a rule.** This is fine — affricates in this list are useful for `[affricate]` to resolve to a list, not for tokenizing. Still, document this. `[VERIFIED: word_generator.dart:241–272]` |

**Recommendation:** Ship the lists in CONTEXT.md essentially as-is, with two adjustments: add ɬ and ɮ to Fricative; document the consonant-only Sonorant as deliberate.

### F-4: Parsed rewrite rule data shape — already sufficient for descriptive allophone listing (HIGH confidence)

**Verified by:** Reading `phonotactic_dsl.dart:309–477` (`PhonologicalRewriteRule` class and `parseRewriteRule` function).

A `PhonologicalRewriteRule` has:

```dart
List<Slot> input;          // LHS — the segment(s) that change
String output;             // RHS — kept as raw string (could be 'ʃ', '[+nasal]', etc.)
List<Slot> leftContext;    // segments before '_'
List<Slot> rightContext;   // segments after '_'
String source;             // original DSL string for round-tripping
```

A `Slot` is `(classReference: String?, literalPhoneme: String?, isOptional: bool)`. For the input slot of a typical rewrite rule, `isOptional` is always false (the parser doesn't allow `(...)` on the LHS — only on syllable templates), so it can be ignored.

**The output is a string, not a Slot list** — by design, since applying transformations is out of scope (D-10/D-13). For the allophone viewer this is exactly what we need: take the output as-is and display it as the realization label. Feature-bundle outputs like `[+nasal]` will appear verbatim as `[+nasal]` (D-13 — opaque label, planner should consider styling them differently per Claude's discretion).

### F-5: Allophone matching algorithm — three cases, deterministic (HIGH confidence)

**Verified by:** Reading the rule data shape above and comparing to the requested behavior in D-11.

Given a phoneme `p` (the `Phoneme` object from the DAO, with `.symbol`) and a parsed `PhonologicalRewriteRule r`, decide whether `r` produces an allophone of `p`:

```dart
bool ruleAffectsPhoneme(PhonologicalRewriteRule r, String phonemeSymbol, NaturalClassResolver resolver) {
  // Case A: Single-segment input that's a literal — must match exactly
  if (r.input.length == 1 && r.input[0].isLiteral) {
    return r.input[0].literalPhoneme == phonemeSymbol;
  }

  // Case B: Single-segment input that's a class reference — class must contain the phoneme
  if (r.input.length == 1 && !r.input[0].isLiteral) {
    final members = resolver.resolve(r.input[0].classReference!);
    return members.contains(phonemeSymbol);
  }

  // Case C: Multi-segment input (cluster like 'st -> ʃt') — recommendation: SKIP
  // Rationale: a cluster rule is not naturally an allophone of a single phoneme.
  // Showing every cluster member as having "allophones" produces noisy/misleading
  // output. Document this as a deliberate omission.
  return false;
}
```

Then the realization label is just `r.output` (D-17 — surface forms only, no contexts).

**Edge cases the planner must address:**

1. **Feature-bundle output (`[+nasal]`):** `r.output == '[+nasal]'`. Display verbatim. Per D-13. Optional: visually distinguish (italic, dimmer color, info icon).
2. **Same output from multiple rules:** Deduplicate by output string (D-12). Use `Set<String>` or `LinkedHashSet` to preserve insertion order.
3. **Identity rule (`a -> a / X_Y`):** Some users may write rules where output equals input. Showing `/a/ → [a]` is technically correct but cluttering. **Recommend filtering out** identity outputs. Trivially implemented with `if (r.output == phonemeSymbol) skip`.
4. **Empty output (`a -> ∅` or `a ->`):** The parser rejects empty outputs (`phonotactic_dsl.dart:402–408`), so this case won't occur. No defensive code needed.
5. **Class output (`a -> [V]`):** Unlikely but parseable. Display verbatim — same path as feature bundles. Per D-13.
6. **Ordering tiebreaker:** When a phoneme has multiple realizations, sort by the rule's `ordering` column (the existing `RewriteRules.ordering` field, ascending). Falls naturally out of `parsedRewriteRulesProvider` since `RewriteRuleDao.watchAll` already orders by `ordering ASC, id ASC`. No extra sort needed — preserve the iteration order.

**Recommended return type:**

```dart
class AllophoneRealization {
  final String output;       // 'ʃ', '[+nasal]', etc.
  final String ruleSource;   // original DSL string, for tooltip / dialog
  final bool isFeatureBundle; // true if output starts with '[' and ends with ']'
}

List<AllophoneRealization> computeAllophones(
  String phonemeSymbol,
  List<PhonologicalRewriteRule> rules,
  NaturalClassResolver resolver,
) { ... }
```

The `ruleSource` field is not displayed in the inline annotation per D-17, but the dialog can use it as a tooltip for users who want to know "which rule produces this realization?" (within the spirit of "surface forms only" — the rule string is supplementary, not primary).

### F-6: Riverpod provider design for reactive allophone computation (HIGH confidence)

**Performance envelope:** ~30–100 phonemes per project × ~10–50 rewrite rules. For each phoneme we walk the rule list once. **Total work per recomputation: ~3,000–5,000 string equality checks. Negligible.**

**Recommended provider topology:**

```dart
// In a new file, e.g. lib/features/phonology/data/allophone_providers.dart

/// Maps each phoneme symbol to its computed allophone realizations.
/// Recomputes whenever the rule list, phoneme inventory, or natural classes change.
final allophoneMapProvider = Provider<Map<String, List<AllophoneRealization>>>((ref) {
  final rules = ref.watch(parsedRewriteRulesProvider);  // already exists
  final inventory = ref.watch(phonemeInventoryProvider); // already exists, will include defaults after F-1 fix
  final phonemes = ref.watch(allPhonemesProvider).asData?.value ?? [];

  final result = <String, List<AllophoneRealization>>{};
  for (final p in phonemes) {
    final realizations = computeAllophones(p.symbol, rules, NaturalClassResolver(inventory));
    if (realizations.isNotEmpty) result[p.symbol] = realizations;
  }
  return result;
});
```

Why a single Map provider rather than a `family` keyed by symbol:

| Approach | Pros | Cons |
|----------|------|------|
| **Single Map provider** (recommended) | One recomputation per change; subscribers select from the map; no provider explosion | Every consumer rebuilds when any rule changes |
| `Provider.family<List, String>` | Fine-grained invalidation per phoneme | Requires the family parameter to equal-compare; needs autoDispose; recomputes per phoneme on each change anyway because the underlying rule list changed |

For this dataset (small, infrequent edits), the simpler single-Map approach wins. Both Phase 1 and Phase 3 use the same pattern (`phonemeInventoryProvider`, `parsedConstraintsProvider` are similarly shaped derived `Provider`s).

**Riverpod version:** flutter_riverpod 3.0.3 + manual `Provider`/`StreamProvider` (not `@riverpod` codegen) — matches the existing project convention documented in `phoneme_providers.dart` and noted in STATE.md ("riverpod_generator 3.x cannot resolve drift part-file types — use manual Provider/StreamProvider for all drift-type providers"). `[VERIFIED: lib/features/phonology/data/phoneme_providers.dart, .planning/STATE.md]`

## Architecture Patterns

### Class resolution layering (the F-1 fix in code)

```dart
// In phonotactic_providers.dart, replace the body of _buildInventory:

import '../domain/default_natural_classes.dart';

PhonemeInventory _buildInventory(
  List<Phoneme> consonants,
  List<Phoneme> vowels,
  List<NaturalClassesData> classes,
) {
  final allPhonemes = [...consonants, ...vowels];
  final idToSymbol = <int, String>{
    for (final p in allPhonemes) p.id: p.symbol,
  };

  // Start with the hardcoded defaults (lowercased keys to match existing convention).
  final naturalClassMap = <String, List<String>>{
    for (final entry in defaultNaturalClasses.entries)
      entry.key.toLowerCase(): entry.value,
  };

  // Single-letter aliases (preserve case so 'S' doesn't collide with literal /s/).
  // These get a SEPARATE map that the resolver checks BEFORE lowercasing.
  // (Implementation requires changing _resolveClass too — see allophone_computer note.)

  // User classes overlay defaults — user wins on collision per D-06.
  for (final cls in classes) {
    try {
      final decoded = jsonDecode(cls.phonemeIds);
      if (decoded is List) {
        final ids = decoded.whereType<int>().toList();
        final symbols = ids
            .map((id) => idToSymbol[id])
            .whereType<String>()
            .toList();
        naturalClassMap[cls.name.toLowerCase()] = symbols;
      }
    } catch (_) {
      // Malformed phonemeIds JSON — skip this class.
    }
  }

  return PhonemeInventory(
    consonants: consonants.map((p) => p.symbol).toList(),
    vowels: vowels.map((p) => p.symbol).toList(),
    naturalClasses: naturalClassMap,
  );
}
```

**Open question for the planner:** Where do single-letter aliases live? Three options:

| Option | Pros | Cons |
|--------|------|------|
| **A.** Add aliases to `naturalClassMap` with their case-sensitive single-letter keys (e.g. `'S' → stops`) and modify `_resolveClass` / `resolvePhonemeClass` to check exact case before lowercasing | Single source; works for all three consumer files | Touches `word_generator.dart` and `morphology_engine.dart` (low risk — both have existing exact-case fallback after the lowercased lookup, but ordering must flip) |
| **B.** Add a second `Map<String, List<String>>` field `aliases` to `PhonemeInventory` and update both resolvers to check `aliases` first | Cleanest separation | Touches `PhonemeInventory` definition + both resolvers + every test fixture that builds it |
| **C.** Skip aliases entirely; ship only full names as defaults (`[stop]`, `[nasal]`, …) | Smallest scope | Violates D-09 ("the full name and the single-letter alias resolve to the same class") |

**Recommendation: Option A.** The existing `_resolveClass` in both `word_generator.dart:213` and `morphology_engine.dart:71` already has a two-tier fallback (lowercased map → exact-case map). Reordering to (exact-case → lowercased) is a one-line edit per file. Then the alias keys (`S`, `N`, etc.) live in the same `naturalClassMap` as the lowercased full names. The user-class overlay still wins because user classes are inserted last, but **only** for full-name collisions. Single-letter aliases are not user-creatable (the validator extension blocks them), so collision is impossible by construction.

### Allophone module (new pure-function code)

```dart
// lib/features/phonology/domain/allophone_computer.dart

class AllophoneRealization {
  const AllophoneRealization({
    required this.output,
    required this.ruleSource,
    required this.isFeatureBundle,
  });

  final String output;
  final String ruleSource;
  final bool isFeatureBundle;

  @override
  bool operator ==(Object other) =>
      other is AllophoneRealization && other.output == output;

  @override
  int get hashCode => output.hashCode;
}

/// Resolves a class reference to its phoneme symbols using the same rules as
/// the runtime DSL resolver. Wraps a [PhonemeInventory] for ergonomic access.
class NaturalClassResolver {
  const NaturalClassResolver(this.inventory);
  final PhonemeInventory inventory;

  List<String> resolve(String classRef) {
    // Reuse the existing resolvePhonemeClass for behavioral parity.
    return resolvePhonemeClass(classRef, inventory);
  }
}

/// Walks [rules] and returns deduplicated realizations of [phonemeSymbol].
///
/// Skips: multi-segment cluster rules, identity rules, rules with no input.
List<AllophoneRealization> computeAllophones(
  String phonemeSymbol,
  List<PhonologicalRewriteRule> rules,
  NaturalClassResolver resolver,
) {
  final out = <AllophoneRealization>[];
  final seen = <String>{};

  for (final r in rules) {
    if (r.input.length != 1) continue;             // skip clusters (Case C)
    final slot = r.input[0];

    final bool matches;
    if (slot.isLiteral) {
      matches = slot.literalPhoneme == phonemeSymbol;
    } else {
      final members = resolver.resolve(slot.classReference!);
      matches = members.contains(phonemeSymbol);
    }
    if (!matches) continue;

    if (r.output == phonemeSymbol) continue;       // skip identity
    if (seen.add(r.output)) {                      // dedup
      out.add(AllophoneRealization(
        output: r.output,
        ruleSource: r.source,
        isFeatureBundle: r.output.startsWith('[') && r.output.endsWith(']'),
      ));
    }
  }
  return out;
}
```

### Anti-patterns to avoid

- **Don't write a new petitparser grammar.** The existing parser handles `[stop]` and `S` already. Defaults are about resolution (the map lookup), not parsing.
- **Don't introduce a new schema migration.** D-03 is explicit. The defaults live in code; the DB is untouched.
- **Don't fall back to deep-coupling the morphology engine to the new module.** `morphology_engine::resolvePhonemeClass` is shared with the lexicon and word generator. The defaults must reach it via the `PhonemeInventory` snapshot it already consumes — not by importing a new module.
- **Don't add allophone display to the lexicon, word generator, or any other surface.** Out of scope per CONTEXT.md "Deferred Ideas — Surfacing allophones outside the inventory page."
- **Don't expand multi-segment cluster rules into per-member allophones.** Returns false → noisy output. Document the deliberate skip in the function doc comment.

## Common Pitfalls

### Pitfall 1: Patching `NaturalClassDao.resolveClass` and assuming the DSL sees the change

**What goes wrong:** The DSL calls `_resolveClass` / `resolvePhonemeClass` via the `PhonemeInventory` snapshot, not via the DAO. Patching the DAO method makes tests pass for the DAO method but breaks nothing — and fixes nothing — at runtime.

**Why it happens:** CONTEXT.md D-05 names the wrong file. The intent is correct ("one resolution integration point"); the file is wrong.

**How to avoid:** Patch `_buildInventory` in `phonotactic_providers.dart`. Patching `resolveClass` is a symmetric, optional addition.

**Warning sign:** If the planner writes a unit test that calls `dao.resolveClass('stop')` and watches it return `[]` from an empty DB, then "fixes" it to return defaults — but never writes an integration test that runs the word generator with a `[stop]` template — the runtime is still broken.

### Pitfall 2: Single-letter alias collisions with literal phonemes

**What goes wrong:** A user adds default class `S` (alias for Stop). They write a rewrite rule `s -> ʃ / _i`. The parser turns `s` into a literal (lowercase), which is correct. But they also write a template `(C)V[s]` thinking `[s]` means literal /s/. The parser interprets `[s]` as a class reference → lowercase → looks up key `s` → returns the default Stops list. Word generator now produces words with arbitrary stops where the user wanted /s/.

**Why it happens:** The parser treats anything inside brackets as a class name, including single lowercase letters.

**How to avoid:** This is a **pre-existing parser quirk** independent of Phase 3.2. The phase should not try to fix it. But the planner should:
1. Document the quirk in `default_natural_classes.dart`'s doc comment.
2. Add a note to `NaturalClassEditor`'s helper text that "single-character bracketed names are interpreted as class references."
3. In the validator extension (rejecting `S`, `N`, `F`, `L`, `R`), explicitly enumerate the reserved single letters so users can't shadow defaults.

**Warning sign:** Any test that uses `[a]` or `[s]` as a literal in a rewrite rule LHS will silently match unrelated phonemes.

### Pitfall 3: Performance death spiral if `allophoneMapProvider` recomputes on every keystroke

**What goes wrong:** The rule editor in `inventory_page.dart` (well, on a different page actually — the rewrite rule editor lives elsewhere) emits stream updates as the user types. If `allophoneMapProvider` watches `parsedRewriteRulesProvider` directly and that provider updates per-keystroke, every chip in the inventory rebuilds on every keystroke.

**Why it happens:** Naive provider topology with no debounce.

**How to avoid:** Verify how `rewriteRuleListProvider` behaves on edit. It's a `StreamProvider` over `dao.watchAll()`, which only fires on database commits — not per-keystroke. The user must save the rule before the stream emits, so debounce is not needed at the provider layer. **Confirmed by reading `rewrite_rule_dao.dart:21–27` and `phonotactic_providers.dart:41–45`.** No action needed, but the planner should verify this assumption holds in the rule editor (the editor probably maintains local TextEditingController state and only commits on save).

**Warning sign:** Profile a session with the Allophone Viewer enabled and the rewrite rule editor open simultaneously. If frame times spike per keystroke, the editor is committing live and a debounce is needed.

### Pitfall 4: Tokenizer fails on out-of-inventory affricate symbols

**What goes wrong:** A user defines an Affricate default that includes `t͡ʃ`. The user has only `t` and `ʃ` as separate phonemes in their inventory. The user writes a rule `t͡ʃ -> ʃ / _#`. The parser stores the LHS as a literal slot with `literalPhoneme = 't͡ʃ'`. The allophone computer correctly matches this against the phoneme `t͡ʃ` — but `t͡ʃ` is **not in the inventory**, so the phoneme dialog will never display it as a row, so no allophone surface ever shows.

**Why it happens:** The default catalog contains symbols the user's inventory doesn't have. This is by design (the entire premise of D-07).

**How to avoid:** The allophone computer is correct — it doesn't matter for allophone display because we only iterate `allPhonemesProvider` (the user's inventory). The defaults are about DSL **input** matching, not phoneme **output** display. Document this clearly in the function doc.

**Warning sign:** A bug report saying "I added a `t͡ʃ -> ʃ` rule and `[affricate]` resolves but no allophone shows for /t͡ʃ/" — the answer is "you didn't add /t͡ʃ/ to your inventory, defaults don't add phonemes."

### Pitfall 5: Alt-held inline annotation overflows the consonant grid cells

**What goes wrong:** The consonant grid uses 56×40 fixed cells (`inventory_page.dart:287–288`). Adding a `→ [b,β]` suffix to a chip can easily double its width, causing horizontal overflow and either layout exception or "RIGHT OVERFLOWED BY Npx" red banners (the project hit this once before in 01-08).

**Why it happens:** Fixed cell sizes vs variable suffix length.

**How to avoid:** Three options for the planner:
1. **Truncate** the suffix to N characters with ellipsis when it exceeds available width (simplest).
2. **Stack** the suffix below the chip text using a `Column` (changes chip aspect ratio).
3. **Tooltip-only** in the dense grid (skip the inline suffix in `_PhonemeCell`, render only in `_AllPhonemesRow` which is a `Wrap` and can grow).

**Warning sign:** Open a project with 5+ phonemes per cell and hold Alt — overflow banners appear.

### Example 2: Modifying `_resolveClass` to check alias map first

```dart
// lib/features/phonology/domain/word_generator.dart — modified

import 'default_natural_classes.dart' show defaultNaturalClassAliases;

List<String> _resolveClass(String classRef, PhonemeInventory inventory) {
  // 1. Reserved system shortcuts.
  switch (classRef) {
    case 'C':
      return inventory.consonants;
    case 'V':
      return inventory.vowels;
  }

  // 2. Single-letter alias (case-sensitive — checked BEFORE lowercasing
  //    so 'S' resolves to Stops without colliding with literal /s/).
  final alias = defaultNaturalClassAliases[classRef];
  if (alias != null) return alias;

  // 3. Lowercased name lookup (existing behavior).
  final key = classRef.toLowerCase();
  if (inventory.naturalClasses.containsKey(key)) {
    return inventory.naturalClasses[key]!;
  }

  // 4. Exact-case fallback (legacy behavior preserved).
  if (inventory.naturalClasses.containsKey(classRef)) {
    return inventory.naturalClasses[classRef]!;
  }

  return [];
}
```

## Open Questions

1. **Should `[s]` (single-letter bracketed lowercase) be reserved as a literal-phoneme escape, or remain a class reference?**
   - What we know: Today the parser treats it as a class reference (returns `[]` if no class named `s` exists). Adding default classes makes this potentially confusing because some lowercase keys (none in the current default set, but theoretically) could collide.
   - What's unclear: Whether to "fix" the parser or document the quirk.
   - Recommendation: Document, don't fix. The fix is a parser change with unknown ripple effect on existing user data. Out of Phase 3.2 scope.

2. **Should the `NaturalClassEditor` validator block exact-case matches of full default names too (e.g. user can't create a class named `stop`), or only block the single-letter aliases?**
   - What we know: D-06 says user classes shadow defaults. Today the validator only blocks `C`/`V`.
   - What's unclear: D-06's "user wins" implies users CAN name a class `stop` to override. Then the validator should NOT block full names — just single-letter aliases.
   - Recommendation: Block only `S`, `N`, `F`, `L`, `R` (and continue blocking `C`, `V`). Allow `stop`, `nasal`, etc. as user overrides per D-06.

3. **Where should `NaturalClassResolver` live: `domain/allophone_computer.dart` (new file) or `domain/word_generator.dart` (existing)?**
