# Phase 3.2: Phonology Enhancements - Context

**Gathered:** 2026-04-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Two focused enhancements to the Phonology tab:

1. **Predefined natural classes** — ship a hardcoded catalog of standard phonological classes (Stop, Nasal, Fricative, Liquid, Rhotic, Obstruent, Sonorant, Approximant, Affricate) with sensible IPA defaults. These classes are always resolvable by name in the existing DSL (e.g. `[stop]`, `[nasal]`) regardless of whether the project's phoneme inventory contains those sounds.

2. **Allophone viewer** — when a user interacts with a phoneme in the inventory, they see the contextual realizations (allophones) derived from the project's existing rewrite rules. Two surfacing points: inside the phoneme dialog popover, and inline next to phoneme chips in the inventory grid when the user holds Alt (same modifier that toggles romanization→IPA display from Phase 3.1).

**Scope reduction:** Requirement PHON-10 (natural classes shareable across languages) has been explicitly removed from this phase. No cross-project/global storage mechanism is introduced. See ROADMAP.md and REQUIREMENTS.md for the out-of-scope marker. Success criterion #2 from the original Phase 3.2 roadmap entry has been removed.

</domain>

<decisions>
## Implementation Decisions

### Scope narrowing (decided 2026-04-10)
- **D-01:** PHON-10 (shareable natural classes across languages) is **out of scope**. No global database, JSON library folder, or import/export mechanism is introduced. REQUIREMENTS.md is updated to mark PHON-10 as out of scope; ROADMAP.md phase description is updated to drop the shareable success criterion.
- **D-02:** Phase 3.2 delivers exactly two things: (1) predefined natural classes including out-of-inventory sounds, (2) contextual allophone viewer on phoneme click + Alt-held inline.

### Predefined natural class storage
- **D-03:** Default classes are **hardcoded in Dart as const data**, not stored as rows in the `NaturalClasses` table. No schema migration required. No seeding on project creation.
- **D-04:** Defaults are **read-only**. Users cannot edit a default class's members; if they want a variant they create a new user-defined class under a different name via the existing `NaturalClassEditor`. Rationale: trivial implementation, predictable behavior, avoids override-tracking infrastructure.
- **D-05:** The class-resolution path (currently `NaturalClassDao.resolveClass(name)`) must be extended so resolution checks the hardcoded defaults when no DB row matches. This is the one load-bearing integration point — every consumer of natural classes (phonotactic DSL, rewrite rules) must see defaults transparently.
- **D-06:** User-defined classes in the DB take precedence over defaults when names collide (allows users to shadow a default locally if they really want to, without editing the defaults). System classes `C`/`V` remain the highest-priority reserved names from Phase 1.

### Predefined class catalog (extended set)
- **D-07:** Ship the following nine hardcoded classes with single-letter DSL abbreviations where the roadmap specified them:
  - **Stop** (alias `S`) — voiceless and voiced plosives across standard POA (p, b, t, d, ʈ, ɖ, c, ɟ, k, ɡ, q, ɢ, ʔ)
  - **Nasal** (alias `N`) — m, ɱ, n, ɳ, ɲ, ŋ, ɴ
  - **Fricative** (alias `F`) — full voiceless+voiced inventory (ɸ, β, f, v, θ, ð, s, z, ʃ, ʒ, ʂ, ʐ, ç, ʝ, x, ɣ, χ, ʁ, ħ, ʕ, h, ɦ)
  - **Liquid** (alias `L`) — l, ɭ, ʎ, ʟ, r, ɾ, ɹ, ɻ, ɽ, ʀ, ʁ (union of lateral approximants, taps/flaps, trills, rhotic approximants)
  - **Rhotic** (alias `R`) — r, ɾ, ɹ, ɻ, ɽ, ʀ, ʁ (the r-family subset of Liquid)
  - **Obstruent** — Stop ∪ Fricative ∪ Affricate
  - **Sonorant** — Nasal ∪ Liquid ∪ Approximant ∪ (vowels implicitly — but do not include vowels in the default list; keep Sonorant consonant-focused to match typical phonological usage)
  - **Approximant** — j, w, ɥ, ɰ, ʋ, ɹ, ɻ, l, ɭ, ʎ, ʟ (lateral + central)
  - **Affricate** — t͡s, d͡z, t͡ʃ, d͡ʒ, ʈ͡ʂ, ɖ͡ʐ, t͡ɕ, d͡ʑ (attached for completeness of the Obstruent set)
- **D-08:** The exact IPA member lists above are the **starting proposal** — the researcher/planner should verify against standard phonological references before finalizing. Additions welcome; removals should be deliberate.
- **D-09:** Both the full name and the single-letter alias resolve to the same class in the DSL (case-sensitive aliases to avoid collision with lowercase phoneme literals).

### Allophone computation
- **D-10:** Allophones are **computed by descriptive listing from the existing parsed rewrite rules** — no SPE rule application engine is built in this phase. The existing `parseRewriteRule` output (with `input`, `output`, `leftContext`, `rightContext`) is sufficient.
- **D-11:** For a given phoneme `/x/`, scan all rewrite rules whose parsed `input` slot list matches a single phoneme literal equal to `x` (or a natural class that contains `x`). For each match, record the rule's `output` string as a realization of `/x/`.
- **D-12:** Deduplicate realizations. The phoneme itself (`/x/ → [x]`) is always implicitly the elsewhere case but is **not shown** when there are no matching rules (per D-18).
- **D-13:** Feature-bundle outputs (e.g. `[+nasal]`) are treated as opaque strings for now — displayed verbatim as the realization label. Resolving them to actual segments is future work (tied to the deferred SPE engine).

### Allophone viewer — surfacing
- **D-14:** **Surface point 1 — phoneme dialog popover.** The existing `phoneme_edit_dialog.dart` (opened via the existing `onTap` on inventory chips) gains an "Allophones" section showing the realization list for that phoneme. The edit-dialog onTap is **not** changed; the allophone view is additive.
- **D-15:** **Surface point 2 — Alt-held inline annotation.** In `inventory_page.dart` consonant/vowel grids, when `_isAltHeld` is true (existing Phase 3.1 state from the `HardwareKeyboard` listener), each phoneme chip shows a compact inline annotation of its allophones next to the IPA glyph. Alt behavior from Phase 3.1 (show IPA instead of romanization) continues; this phase composes on top.
- **D-16:** The Alt-held inline annotation is **compact by design** — a small secondary-color subscript/suffix that shouldn't crowd the grid layout (existing chips are tight). Exact spacing and typography is Claude's discretion.

### Allophone viewer — content
- **D-17:** **Format: surface forms only.** Both surface points show `/x/ → [a, b, c]` — the realization forms without the contexts or rule strings. Keeps the inline view compact and the popover readable.
- **D-18:** **Empty state: blank.** A phoneme with no matching rewrite rules shows **nothing** (no label, no fallback `[x]`). This is intentional — phonemes with interesting allophony draw the eye, the rest stay clean.
- **D-19:** Format uses slash/bracket convention: underlying phoneme in `/slashes/`, realizations in `[brackets]`. Multiple realizations are comma-separated inside a single bracket pair: `/s/ → [s, z, ʃ]`.

### Claude's Discretion
- Exact typography, spacing, and color of the inline Alt-held allophone annotation
- Layout of the "Allophones" section within the phoneme edit dialog (list vs. inline chips vs. grid)
- Whether the DSL aliases are matched case-sensitively or case-insensitively (D-09 recommends case-sensitive — planner may revisit if it breaks existing usage)
- How feature-bundle outputs (`[+nasal]`) are visually distinguished in the allophone list (italic? warning icon?) — or whether they're hidden entirely
- Tiebreaker ordering when a phoneme has multiple rules and thus multiple realizations (probably rule `ordering` column)
- Whether to expose the full default catalog in the existing `natural_class_editor.dart` "System classes notice" area, or only via DSL

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`NaturalClassDao.resolveClass(name)`** — single resolution call-site for DSL lookups. Extend this one method with a hardcoded-defaults fallback and every consumer (phonotactic templates, rewrite rules, future morphology rules) picks up defaults automatically.
- **`parseRewriteRule` + `PhonologicalRewriteRule`** — already produces the structured input/output/context data needed to list allophones. No new parser work required.
- **`_isAltHeld` state + `HardwareKeyboard.instance.addHandler` pattern** in `inventory_page.dart` (Phase 3.1) — reuse as-is for the inline annotation trigger.
- **`phoneme_edit_dialog.dart`** — already opened on chip tap; gains a new section rather than a new dialog.

### Established Patterns
- Drift DAO + Riverpod `StreamProvider` for reactive data — no change; allophone listing is a derived computation over the existing `rewriteRulesProvider` and `allPhonemesProvider`.
- `const` data constants in Dart files for static reference data (see `ipa_data.dart` for the precedent on hardcoded phonetic data).
- Alt-modifier as reveal-extra-info convention (Phase 3.1) — D-15 extends this consistently.

### Integration Points
- **`NaturalClassDao.resolveClass`** — fallback-to-defaults (D-05). This is THE load-bearing integration point.
- **Allophone computation module** (new) — pure function `List<AllophoneRealization> computeAllophones(Phoneme p, List<PhonologicalRewriteRule> rules, NaturalClassResolver ncr)`. Lives in `lib/features/phonology/domain/`. Consumed by both surface points.
- **`inventory_page.dart`** — compose inline annotation into each phoneme chip builder when `_isAltHeld` is true.
- **`phoneme_edit_dialog.dart`** — new Allophones section reading from the same computation.
- **`natural_class_editor.dart`** — optional: surface the default catalog as a read-only discovery list (Claude's discretion).

### Known non-issues
- No database migration is needed — the schema is untouched.
- No provider graph changes are needed beyond adding one derived provider for the computed allophone list.
- No new routes or navigation entries — both surface points are in the existing inventory page.

</code_context>

<specifics>
## Specific Ideas

- "I don't want shareable or cross-project classes" — explicit descoping of PHON-10. The whole global-storage question is dropped.
- "Just make new default classes that contain phonemes that may not be in the inventory" — the user wants defaults to just *work* at the DSL level regardless of the project's inventory. Hardcoded-in-Dart is the simplest realization of that intent.
- "I want to see the allophones" — core user intent for PHON-11. No elaborate UI wanted.
- "Both in the popover of the phoneme, and next to it in the charts when holding alt (since alt shows the phoneme instead of its romanization)" — explicit dual surfacing, tightly coupled to the Phase 3.1 Alt-held IPA reveal.

</specifics>

<deferred>
## Deferred Ideas

- **Shareable / cross-project natural classes (PHON-10)** — explicitly out of scope for this phase per user decision 2026-04-10. Not on the near-term roadmap. If revived, the natural place is a future "library/globals" phase.
- **SPE rule application engine** — actually transforming segments through rewrite rules. Would upgrade the allophone viewer from descriptive listing (D-10) to computed surface forms. Belongs in a future "phonology engine" phase or merges with the morphology engine work.
- **Feature-bundle resolution** — rules like `V -> [+nasal] / _N` currently produce an opaque `[+nasal]` label in the allophone viewer (D-13). Resolving feature bundles to concrete segments requires a featural phonology model — future work.
- **Editable default classes / reset-to-defaults flow** — rejected in D-04 in favor of read-only simplicity. Can be added later if users complain.
- **Surfacing allophones outside the inventory page** (e.g. on lexicon words, in the word generator) — not discussed; out of scope unless the user raises it.
- **Worked examples per rule** (e.g. `asa → aza` next to `s → z / V_V`) — considered as a "hybrid" computation option and rejected in favor of the simpler descriptive listing.

</deferred>
